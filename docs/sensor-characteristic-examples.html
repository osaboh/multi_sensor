センサー値 → BLEキャラクタリスティック 変換例

データの流れ（物理値 → I2C生バイト → BLEキャラクタリスティックのバイト列）を全センサーで具体例として示す。

1. LPS22HB（気圧・温度）

adv_env/device.ino の実装をそのまま踏襲: 気圧は24bit符号なし(÷4096=hPa)、温度は16bit符号付き(÷100=℃)。

例: 気圧 1006.00 hPa, 温度 22.50℃

レジスタ生値計算
PRESS_OUT (0x28-0x2A)XL/L/H00 E0 3Eraw=0x3EE000=4,120,576 → 4,120,576÷4096=1006.00 hPa
TEMP_OUT (0x2B-0x2C)L/HCA 08raw=0x08CA=2250 → 2250÷100=22.50℃

キャラクタリスティック値 (a0b40121, int16 LE × 2):

  • 温度: LPS22HBのレジスタが既に「÷100=℃」形式 → 生レジスタ値をそのままコピーするだけ（CA 08 → 2250 → 22.50℃）
  • 気圧: そのまま送るとint16に収まらない（1006×100=100600 > 32767）ので、adv_env.ino と同じ「標準大気圧との差分×100」方式を使う（絶対値×100は不可）
    (1006.00 − 1013.25) × 100 = −725 → 0xFD2B → LE 2B FD
送信バイト列: 2B FD CA 08

2. HDC2010（温度・湿度）

16bit符号なし、線形マッピング（温度: 0〜65535 → −40〜125℃、湿度: 0〜65535 → 0〜100%）。LPS22HBと違い生レジスタ値とキャラクタリスティック値が一致しない。

例: 温度 23.48℃, 湿度 55.20%RH

レジスタ生値計算
TEMP (0x00-0x01)LSB/MSB7C 62raw=0x627C=25212 → 25212×165/65536−40=23.48℃
HUMID (0x02-0x03)LSB/MSB50 8Draw=0x8D50=36176 → 36176×100/65536=55.20%

キャラクタリスティック値 (a0b40122, int16 LE ×100 × 2):

  • 温度: 23.48×100=2348 → 0x092C → LE 2C 09
  • 湿度: 55.20×100=5520 → 0x1590 → LE 90 15
送信バイト列: 2C 09 90 15（生レジスタの 7C 62 50 8D とは別物）

3. BMX055 加速度計（±2g設定, 感度0.98 mg/LSB, 12bit）

生の16bitレジスタは12bit値を4bit左シフトして格納（下位4bitは予備/new-dataフラグ、読み出し時に >>4 で捨てる）。

例: X=+50mg, Y=−20mg, Z=+1000mg(≒1G, 静止時)

raw(12bit) = 物理値[mg] ÷ 0.98mg：X=51, Y=−20, Z=1020

軸レジスタ(LSB/MSB)生バイト12bit復元値
X (0x02-0x03)30 03raw16=0x0330(=51<<4)51
Y (0x04-0x05)C0 FEraw16=0xFEC0(=−20<<4)−20
Z (0x06-0x07)C0 3Fraw16=0x3FC0(=1020<<4)1020
キャラクタリスティック値: 現行設計（生カウント値のまま送信）だと int16 LE で 33 00 EC FF FC 03（51, −20, 1020）。物理値(g)への変換はアプリ側で raw×0.98mg を想定。

4. BMX055 ジャイロ（±2000°/s設定, 感度16.4 LSB/(°/s), 16bit）

加速度と違いシフト無しの素の16bit符号付き値。

例: X=+10°/s, Y=−5°/s, Z=0°/s

raw = 物理値[°/s] × 16.4：X=164, Y=−82, Z=0

軸レジスタ(LSB/MSB)生バイト
X (0x02-0x03)A4 00raw=164
Y (0x04-0x05)AE FFraw=−82
Z (0x06-0x07)00 00raw=0
キャラクタリスティック値: 生カウントそのまま int16 LE A4 00 AE FF 00 00。物理値(°/s)はアプリ側で raw÷16.4。

5. BMX055 磁力計（ファームウェア側で補正、µT値を送る — 決定済み）

X/Y/Zは13bit/13bit/15bit(RHALL含む)の生カウントだが、単純な倍率変換ができない。物理値(µT)へ正しく変換するには工場出荷時のトリム値（dig_x1, dig_x2, dig_y1, dig_y2, dig_z1〜z4, dig_xyz1 など、チップごとに個体差のある補正レジスタ）を使った専用の補正計算（Bosch互換のBMM050系補正アルゴリズム）が必須。単純な「LSBあたり◯µT」という係数は存在しない（mRes=1/1.6 という簡易スケールも補正後の値にのみ適用するもの）。

方針: ファームウェア側でトリム値読み出し＋補正計算を実装し、µT単位に変換してからcharacteristicで送る。

理由（計算コスト試算）:

  • Bosch公式ドライバの補正関数(X/Y/Z軸ごと)は乗除算あわせて10〜15回程度の単精度浮動小数点演算のみ。nRF52840(Cortex-M4F, ハードウェアFPU搭載)なら3軸まとめても数百サイクル(数マイクロ秒)のオーダーで、1秒間隔のNotifyには対してまったく無視できるコスト
  • トリム値読み出しは起動時に一度、レジスタ14個程度をI2Cで読むだけ
  • 一方、トリム値をcharacteristicで公開してクライアント側に補正を任せる案は、iOSアプリ/Androidアプリ/Pythonスクリプトなどクライアントの数だけ補正ロジックを重複実装することになり、符号・スケールを間違えるリスクが上がる上にBLEプロファイルも複雑になる（トリム値を読む手順が別途必要）。計算コストが実質ゼロである以上、ファームウェア側で一度だけ正しく実装する方が合理的

他の4Service（LPS22HB/HDC2010/加速度/ジャイロ）も物理値をそのまま返す設計なので、一貫性の面でもこの方針に合わせる。
